Module 0.1 — Complexity Analysis & Big-O

Before learning a single data structure, you need the measuring tape: a way to say how fast and how memory-hungry code is, independent of your laptop. That measuring tape is Big-O.

1. Why this exists

Analogy. Imagine two cooking recipes for the same dish. Recipe A says: "for each guest, chop one onion." Recipe B says: "for each guest, chop one onion per other guest." With 4 guests, A needs 4 onions and B needs 12. With 100 guests, A needs 100 and B needs 9,900. The recipes don't just differ in speed — they differ in how their cost grows as the party grows. Big-O is the language for describing that growth.

The problem it solves. "My code ran in 2 seconds" is nearly meaningless: a faster computer, a different language, or a smaller input changes the number. We need a measure that ignores the machine and captures the only thing that survives all those changes: how the number of steps grows as the input size n grows. Without it, you can't compare two algorithms, and you can't predict whether code that works on 1,000 items will survive 10,000,000.

Plain-English definition. Big-O notation describes the growth rate of an algorithm's step count (or memory use) as a function of input size n, keeping only the dominant term and dropping constant factors. "This is O(n²)" means: for large inputs, the work grows roughly like n squared.

2. Counting steps — the core skill

A "step" is any constant-time action: an arithmetic operation, a comparison, an assignment, reading one array slot. To analyze code, count how many steps run as a function of n.

def total(nums):          # n = len(nums)
    s = 0                 # 1 step
    for x in nums:        # loop body runs n times
        s += x            # 1 step each time  → n steps
    return s              # 1 step
                          # total: n + 2 steps → O(n)

Why do we throw away the "+2" and any constant multiplier? Because growth is what matters: when n = 1,000,000, the difference between n and n+2 is invisible, but the difference between n and n² is the difference between an instant and three hours.

Growth of steps as n doubles:

  O(1)        1 → 1          (unchanged — constant)
  O(log n)    20 → 21        (+1 — barely moves)
  O(n)        1000 → 2000    (doubles)
  O(n log n)  10k → 21k      (slightly worse than double)
  O(n²)       1M → 4M        (quadruples!)
  O(2ⁿ)       …doubles for EVERY +1 of n (catastrophic)

The common complexity classes, slowest-growing first

ClassNameTypical sourcen = 1,000,000 → steps ≈

O(log n)Logarithmicbinary search, balanced-tree ops20

Interview rule of thumbRoughly 10⁷–10⁸ simple steps per second is a safe mental budget. If n ≤ 10⁵, an O(n²) = 10¹⁰ solution will time out, but O(n log n) ≈ 1.7×10⁶ is comfortable. Constraints in a problem statement are a hint about the expected complexity.

3. Analyzing loops — dry runs

Single loop → O(n)

for i in range(n):    # runs n times
    print(i)          # O(1) work each → O(n) total

Nested loop over the same input → O(n²)

for i in range(n):        # n iterations
    for j in range(n):    # n iterations EACH
        print(i, j)       # runs n × n = n² times → O(n²)

Triangular nested loop → still O(n²)

for i in range(n):
    for j in range(i):    # runs 0, then 1, then 2, ... then n-1 times
        print(i, j)

Dry run with n = 5: inner runs 0+1+2+3+4 = 10 times. In general 0+1+…+(n−1) = n(n−1)/2 ≈ n²/2. Drop the constant ½ → O(n²). Why: half of a quadratic is still quadratic growth.

Two sequential loops → O(n), not O(n²)

for i in range(n): ...    # n steps
for j in range(n): ...    # then n more steps
# total 2n → O(n). Loops one AFTER another ADD; loops INSIDE each other MULTIPLY.

Loop that halves → O(log n)

i = n
while i > 1:
    i = i // 2     # n → n/2 → n/4 → ... → 1

Dry run with n = 32: i takes values 32, 16, 8, 4, 2, 1 — that's 5 halvings, and log₂(32) = 5. Why log: "how many times can I halve n before reaching 1?" is the definition of log₂ n.

Log intuitionlog₂ n answers: "how many times must I double 1 to reach n?" or equivalently "how many digits does n have in binary?" It grows absurdly slowly: log₂ of one billion is ~30. Whenever an algorithm discards half the remaining input each step (binary search, heaps, balanced trees), a log appears.

Loop with two moving pointers → O(n)

left, right = 0, n - 1
while left < right:        # each iteration moves left OR right
    ...                    # pointers can move at most n total steps

Why: count total pointer movement, not iterations of some imagined nested structure. The two pointers travel at most n slots combined → O(n). This trick powers the Two Pointers and Sliding Window patterns.

4. Best, average, worst case

Analogy. Searching for your keys: best case they're in your pocket (1 step), worst case they're in the last drawer you check (every drawer), average case somewhere in the middle.

def linear_search(nums, target):
    for i, x in enumerate(nums):
        if x == target:
            return i        # found — stop early
    return -1
  • Best case — target is at index 0: O(1).
  • Worst case — target is absent: all n checked, O(n).
  • Average case — target equally likely anywhere: ~n/2 checks → O(n).

Unless stated otherwise, Big-O in interviews means worst case — you're promising "never slower than this." The famous exception is quicksort and hashing, which are quoted by average case because their worst cases are rare in practice (and we say so explicitly).

5. Amortized analysis

Analogy. A coffee shop punch card: 9 coffees at $5, the 10th free. Each individual purchase isn't $5 — one of them is $0 — but the average over the sequence is $4.50. Amortized cost is the cost of an operation averaged over a worst-case sequence of operations.

The classic example: dynamic array append. Python's list.append is usually O(1) — write into a spare slot. But when the array is full, it allocates a bigger array (typically ~2×) and copies all n elements: that one append costs O(n).

Appending 1..9 with capacity doubling (copy cost shown):

  cap 1:  [1]                 append #1: cost 1
  cap 2:  [1,2]               append #2: copy 1 + insert  = 2
  cap 4:  [1,2,3]_            append #3: copy 2 + insert  = 3
          [1,2,3,4]           append #4: cost 1
  cap 8:  [1,2,3,4,5]___      append #5: copy 4 + insert  = 5
          ... appends #6,7,8: cost 1 each

  Total for n appends ≈ n (inserts) + (1+2+4+...+n/2) (copies) ≤ 2n
  → 2n steps / n appends = O(1) amortized per append

Why it works: the expensive copies happen exponentially rarely — each doubling buys you that many cheap appends before the next copy. The total copy work (1+2+4+…+n) is bounded by 2n, so spread across n appends it adds only a constant per operation.

PitfallAmortized O(1) is not the same as "always O(1)." A single append can still take O(n) time. That matters in real-time systems, but for total-runtime analysis you may treat amortized O(1) as O(1).

6. Space complexity

Plain English: how much extra memory the algorithm allocates, as a function of n. The input itself is usually not counted; we count what you add on top (called auxiliary space).

def reverse_in_place(nums):       # O(1) space: only two integer variables
    l, r = 0, len(nums) - 1
    while l < r:
        nums[l], nums[r] = nums[r], nums[l]
        l += 1; r -= 1

def reversed_copy(nums):          # O(n) space: builds a whole new list
    return nums[::-1]

Recursion costs space too. Every active call sits on the call stack. A recursion that goes n levels deep uses O(n) space even if it allocates nothing — the stack frames are the memory. (Module 0.6 visualizes this.)

Time–space trade-offMany patterns (hashing, memoization, prefix sums) deliberately spend O(n) memory to cut time from O(n²) to O(n). Being able to say "I can make this faster if I'm allowed extra memory" is an interview superpower.

7. Analyzing recursion — the recursion tree

For loops you count iterations; for recursion you count calls × work per call. Draw the tree of calls.

Example 1: halving with O(1) work — binary search

def bsearch(nums, lo, hi, t):
    if lo > hi: return -1
    mid = (lo + hi) // 2
    if nums[mid] == t: return mid
    if nums[mid] < t:  return bsearch(nums, mid+1, hi, t)   # one recursive call
    return bsearch(nums, lo, mid-1, t)                      # (only one runs)
n → n/2 → n/4 → ... → 1     one branch, log n levels, O(1) work each
TIME O(log n) · SPACE O(log n) call stack

Example 2: halving with O(n) work — merge sort

Level 0:            [········ n ········]      merge work: n
Level 1:        [···· n/2 ····][···· n/2 ····]  work: n/2 + n/2 = n
Level 2:      [n/4][n/4][n/4][n/4]              work: n
  ...                                            every level totals n
Level log n:  [1][1][1] ... [1]

log n levels × n work per level = O(n log n)

Example 3: branching by 2 without shrinking fast — naive Fibonacci

def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)    # TWO calls, input shrinks by only 1
                 fib(5)
              /        \
         fib(4)        fib(3)
         /    \        /    \
     fib(3)  fib(2) fib(2) fib(1)
     ...
Each level roughly DOUBLES the number of calls → ~2ⁿ calls → O(2ⁿ)
(fib(2) is computed 3 times already — DP exists to fix exactly this.)
Master-theorem intuition (no formula memorization needed) For divide-and-conquer T(n) = a·T(n/b) + work(n), compare the two forces: how fast subproblems multiply (a per level) vs how fast work shrinks. Three outcomes:
  • Leaves dominate — branching wins (e.g. T(n)=2T(n/2)+O(1)) → cost ≈ number of leaves → O(n).
  • Every level equal — perfectly balanced (e.g. merge sort, 2T(n/2)+O(n)) → level cost × log n levels → O(n log n).
  • Root dominates — top-level work dwarfs the rest (e.g. T(n)=T(n/2)+O(n)) → O(n).
Ask: "is the total work growing, constant, or shrinking as I go down the tree?" That answers the recurrence.

8. Comparing growth rates & common confusions

ConfusionClarification
O(n) vs O(2n)Identical. Constants are dropped — both are O(n).
O(n² + n)= O(n²). Only the dominant term survives; for large n the n is noise.
O(log₂ n) vs O(log₁₀ n)Identical. Different log bases differ by a constant factor — we just write O(log n).
O(n + m)Keep both! Two independent input sizes (e.g. two strings) can't be merged.
Best case = Big-O?No. Big-O conventionally reports worst case unless you say otherwise.
"O(1) means fast"It means doesn't grow with n. An O(1) op could still be slow in absolute terms (e.g. a fixed 1000-step computation).

9. Edge cases & classic beginner mistakes

  • Hidden loops inside library calls. x in list is O(n), x in set is O(1) average. list.insert(0, v) is O(n) (shifts everything). sorted() is O(n log n). String concatenation in a loop (s += c) is O(n²) total because strings are immutable — each += copies. Count the library's work, not just your own lines.
  • Slicing copies. nums[1:] allocates a new list — an innocent-looking recursion that slices each call turns O(n) into O(n²).
  • Multiplying when you should add. Sequential loops add; only nested loops multiply.
  • Forgetting recursion's stack space. Depth-n recursion is O(n) space, and Python's default recursion limit (~1000) will crash on deep inputs.
  • Analyzing iterations instead of total work. In two-pointer / sliding-window loops, bound the total movement of the pointers, not "loop inside loop = n²."

10. Check yourself

Q1. Complexity of this code? for i in range(n): for j in range(100): work()

O(n). The inner loop is a constant 100 iterations — constants are dropped. Nested does not automatically mean n².

Q2. i = 1; while i < n: i = i * 3 — how many iterations?

O(log n) (base 3, but base doesn't matter). i takes values 1, 3, 9, 27, … — the number of triplings to reach n is log₃ n.

Q3. You append n items to a Python list. Total time?

O(n) total — O(1) amortized per append. Resizing copies cost at most 1+2+4+…+n ≤ 2n across the whole sequence.

Q4. Recursive function makes 2 calls on input n−1 with O(1) work. Complexity?

O(2ⁿ). Calls double every level and there are n levels — that's the naive-Fibonacci shape.

Q5. Merge two sorted lists of lengths n and m by walking both once. Complexity?

O(n + m) time, O(n + m) space for the output. Two independent sizes stay separate.
