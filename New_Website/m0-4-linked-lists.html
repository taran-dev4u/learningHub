Module 0.4 — Linked Lists (Singly, Doubly, Circular)

The first structure you'll build out of pointers instead of contiguous memory. Linked lists trade away instant indexing to gain instant insertion and deletion — and they teach the pointer-surgery skills every later structure depends on.

1. Why this exists

Analogy. A treasure hunt. Each clue contains some loot and the location of the next clue. The clues can be scattered anywhere in the city — what holds the hunt together isn't physical closeness (like array slots) but the chain of "next" directions. To add a stop mid-hunt, you rewrite exactly one clue. Nobody else moves.

The problem it solves. Arrays (Module 0.2) pay O(n) to insert or delete anywhere but the end, because contiguity forces shifting. A linked list makes insertion and deletion O(1) once you're standing at the right spot — you just rewire two pointers. The price: finding a position now costs O(n), because there's no address formula; you must follow the chain.

Plain-English definition. A linked list is a chain of nodes. Each node holds a value and a reference (pointer) to the next node. The list itself is just a pointer to the first node (the head). The last node points to None — the end of the hunt.

Node anatomy & memory picture

Array — one contiguous block:        Linked list — nodes scattered anywhere:

  [10][20][30][40]                      head ─→ ┌────┬───┐     ┌────┬───┐
   addresses 1000..1015                         │ 10 │ ●─┼──→  │ 20 │ ●─┼──→ ...
                                                └────┴───┘     └────┴───┘
                                                addr 7042      addr 1336
                                       value + next-pointer; addresses irrelevant
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val      # the loot
        self.next = next    # the clue to the next node (None = end of list)

2. Singly linked list — every operation

2.1 Create / initialize

# build 1 → 2 → 3 by hand:
head = ListNode(1, ListNode(2, ListNode(3)))

# or from a Python list, front to back:
def build(values):
    head = None
    for v in reversed(values):     # build backward: each new node
        head = ListNode(v, head)   # becomes the new head, pointing at the rest
    return head                    # O(n)

2.2 Traverse — O(n)

The universal loop. You'll write this a thousand times:

cur = head
while cur:               # stops when cur is None (we walked off the end)
    print(cur.val)
    cur = cur.next       # follow the clue

Dry run on 1→2→3: cur=node(1), print 1 → cur=node(2), print 2 → cur=node(3), print 3 → cur=None, stop. Each node visited once → O(n) time, O(1) space.

2.3 Search / access — O(n)

def find(head, target):          # by value
    cur = head
    while cur:
        if cur.val == target:
            return cur           # the node itself, not an index
        cur = cur.next
    return None

def get_at(head, i):             # by position — NO formula, must walk
    cur = head
    for _ in range(i):
        if cur is None: return None    # i out of range
        cur = cur.next
    return cur

Why O(n): nodes live at arbitrary addresses; the only way to reach node i is to follow i pointers. This is the price paid for cheap insertion.

2.4 Insert

Analogy: adding a stop to the treasure hunt — write a new clue, point it at the old next stop, and rewrite the previous clue to point at you. Order matters: connect the new node first, or you lose the rest of the chain.

insert 99 after node A (the two-step rewire):

  before:   A ─→ B ─→ C            new = ListNode(99)

  step 1:   new.next = A.next      A ─→ B          (new) ──→ B
                                                    99 grabs B FIRST
  step 2:   A.next = new           A ─→ (99) ─→ B ─→ C   ✓

  WRONG ORDER: A.next = new first  →  B and C are unreachable. Lost forever.
def insert_at_head(head, v):        # O(1) — the linked list's superpower
    return ListNode(v, head)        # new node points at old head; return new head

def insert_after(node, v):          # O(1) given the node
    node.next = ListNode(v, node.next)   # both steps in one line, safe order

def insert_at_tail(head, v):        # O(n): must walk to the end first
    if head is None:
        return ListNode(v)          # empty list: new node IS the list
    cur = head
    while cur.next:                 # stop at the LAST node (next is None)
        cur = cur.next
    cur.next = ListNode(v)
    return head

def insert_at(head, i, v):          # at position i: walk i-1 steps, then splice
    if i == 0:
        return ListNode(v, head)
    cur = head
    for _ in range(i - 1):          # stand on node i-1
        cur = cur.next              # (raises if i > length — caller's problem)
    cur.next = ListNode(v, cur.next)
    return head

Complexity: head O(1); after a known node O(1); tail O(n) (O(1) if you cache a tail pointer); position i O(i). Why: rewiring is constant work — all cost is in getting there.

2.5 Delete

Key insight: to delete node X you must be standing on the node before X — only it can bypass X. (A singly linked node can't unlink itself; it doesn't know who points at it.)

delete B (standing on A):

  before:   A ─→ B ─→ C
  rewire:   A.next = A.next.next         A ────────→ C
  after:    A ─→ C        (B has no incoming pointers → garbage collected)
def delete_head(head):              # O(1)
    return head.next if head else None

def delete_value(head, target):     # first occurrence, O(n)
    if head is None:
        return None
    if head.val == target:          # special case: victim is the head,
        return head.next            # there is no "node before" it
    prev = head
    while prev.next and prev.next.val != target:
        prev = prev.next            # stop on the node BEFORE the victim
    if prev.next:                   # found it (else target absent — no-op)
        prev.next = prev.next.next  # bypass
    return head

Dry run: delete 2 from 1→2→3. head.val=1≠2 → prev=node(1); prev.next.val=2=target → stop. prev.next = node(2).next = node(3). List: 1→3. ✓

2.6 Update / modify — O(n) to find, O(1) to change

node = find(head, 20)
if node: node.val = 99       # overwriting a found node's value is O(1)

3. The dummy-node trick

Notice how delete_value needed a special case for the head? Every "what if the change happens at position 0?" branch disappears with one idea: park a fake node in front of the head. Now every real node has a node before it, and one code path handles all cases.

dummy ─→ 1 ─→ 2 ─→ 3
  ▲ not real data — just a handle so the head is no longer special
return dummy.next   ← the real head (whatever it has become)
def delete_value(head, target):
    dummy = ListNode(0, head)       # sits before the head
    prev = dummy
    while prev.next:
        if prev.next.val == target:
            prev.next = prev.next.next   # works even when victim is the head!
            break
        prev = prev.next
    return dummy.next               # NEVER return head — it may be deleted
When to reach for a dummyAny time an operation might modify the head: deleting, inserting at front under conditions, merging lists, partitioning. Rule of thumb: if you catch yourself writing if head is None or head.val == … as a special case, use a dummy instead. This trick appears in half of P3's problems.

4. Doubly linked lists

Analogy. A treasure hunt where every clue also records where you came from — you can walk the hunt in reverse.

What changes: each node gains a prev pointer. Now a node can remove itself (it knows both neighbors), and you can traverse backward. The cost: every insert/delete must maintain four pointer updates instead of two, and each node spends extra memory.

        ┌──────────────┐    ┌──────────────┐
None ←──┤ prev  10 next ├──→┤ prev  20 next ├──→ None
        └──────────────┘ ←──└──────────────┘
              head                tail
class DNode:
    def __init__(self, val=0):
        self.val = val
        self.prev = None
        self.next = None

class DoublyLinkedList:
    def __init__(self):
        # TWO sentinels: head and tail dummies. No edge cases anywhere.
        self.head = DNode()          # before first real node
        self.tail = DNode()          # after last real node
        self.head.next = self.tail
        self.tail.prev = self.head

    def insert_after(self, node, v):     # O(1): rewire 4 pointers
        new = DNode(v)
        nxt = node.next
        new.prev = node                  # 1. new looks back at node
        new.next = nxt                   # 2. new looks forward at nxt
        node.next = new                  # 3. node points forward to new
        nxt.prev = new                   # 4. nxt points back to new
        return new

    def remove(self, node):              # O(1) — no walk needed!
        node.prev.next = node.next       # bypass forward
        node.next.prev = node.prev       # bypass backward

    def push_front(self, v): return self.insert_after(self.head, v)
    def push_back(self, v):  return self.insert_after(self.tail.prev, v)
    def pop_front(self):
        if self.head.next is self.tail: raise IndexError("empty")
        node = self.head.next; self.remove(node); return node.val
    def pop_back(self):
        if self.tail.prev is self.head: raise IndexError("empty")
        node = self.tail.prev; self.remove(node); return node.val

Dry run of insert_after(head, 10) on an empty list: new=DNode(10); nxt=tail. new.prev=head, new.next=tail, head.next=new, tail.prev=new. Chain: head⇄10⇄tail. ✓ The sentinels meant zero special cases.

Why doubly mattersremove(node) in O(1) given only the node is the heart of the LRU Cache (P18): a hash map jumps straight to a node, the doubly linked list unhooks it instantly. Hash map + DLL = O(1) everything.

5. Circular linked lists

What changes: the tail points back to the head instead of None. There is no end — useful for things that cycle forever: round-robin schedulers, multiplayer turn order, fixed-size ring buffers.

      ┌────────────────────────┐
      ▼                        │
     [1] ─→ [2] ─→ [3] ─→ [4] ─┘     traversal: stop when you RETURN to start
                                      (a "while cur:" loop never ends!)
def traverse_circular(head):
    if head is None: return
    cur = head
    while True:
        print(cur.val)
        cur = cur.next
        if cur is head:          # back where we started → done exactly one lap
            break
PitfallEvery loop on a circular list needs an explicit stop condition (cur is head) or a counter. The standard while cur: idiom spins forever — the same bug that makes accidental cycles dangerous in problems (detected with Fast & Slow pointers, P1.4).

6. The signature move: in-place reversal

The most-asked linked-list operation in interviews — and the gateway to P3.1. Walk the list once, flipping each arrow as you pass:

def reverse(head):
    prev = None                  # everything BEHIND me, already reversed
    cur = head                   # node I'm flipping now
    while cur:
        nxt = cur.next           # 1. save the rest BEFORE breaking the link
        cur.next = prev          # 2. flip my arrow backward
        prev = cur               # 3. advance prev to me
        cur = nxt                # 4. step into the saved rest
    return prev                  # cur fell off the end; prev is the new head
reverse 1→2→3, state after each iteration (prev | cur):

  start:        None | 1 → 2 → 3
  after it 1:   None ← 1 | 2 → 3
  after it 2:   None ← 1 ← 2 | 3
  after it 3:   None ← 1 ← 2 ← 3 | ∅      return prev = node(3):  3→2→1 ✓

O(n) time, O(1) space — no new nodes, just rewired arrows. Memorize the four-line body; dry-run it on two nodes until it's reflex.

Honest practical note: arrays win most real-world benchmarks because contiguous memory is cache-friendly. Linked lists win when you hold a node and must insert/delete at it in guaranteed O(1) — and as the building block of stacks, queues, chained hash tables, and LRU caches.

8. Edge cases & classic mistakes

  • Empty list (head is None) — does your function survive? Test it first, always.
  • Single node — head is tail; reversal/deletion must still work.
  • Operating on the head without a dummy — the #1 source of special-case bugs.
  • Losing the chain: overwriting .next before saving it. Always nxt = cur.next first.
  • Returning the old head after a mutation that may have replaced it. Return dummy.next.
  • Null-pointer steps: cur.next.next crashes when cur.next is None — guard chains of dots.
  • Infinite loop on circular lists (or lists with an accidental cycle).
  • Doubly: updating only 2 of the 4 pointers — the list still "works" forward but is corrupt backward; bugs surface much later.

9. When to use / recognition signals

Reach for a linked list when…the problem hands you one (LeetCode says ListNode — no choice!), you need O(1) insert/delete at a held position (LRU cache, schedulers), or you need a structure that never reallocates (stable node references).
Avoid when…you need indexing or binary search (arrays), or memory locality matters more than splice speed (almost always in practice — Python lists beat linked lists for general storage).

10. Check yourself

Q1. Why is insert-at-head O(1) for a linked list but O(n) for an array?

The list just creates a node pointing at the old head — two pointer writes, nothing moves. The array must shift all n elements right to keep contiguity.

Q2. To delete node X from a singly list, why do you need the node before X?

Deletion means making X unreachable — someone must rewire the pointer into X. Only X's predecessor holds that pointer, and singly nodes can't look backward. (A doubly node knows its prev, so it can unhook itself in O(1).)

Q3. In the reversal loop, what breaks if you skip nxt = cur.next?

cur.next = prev overwrites the only pointer to the rest of the list. Everything after cur becomes unreachable, and the loop can't advance.

Q4. What problem does a dummy node solve?

It guarantees every real node has a predecessor, so head-modifying operations need no special case. You return dummy.next as the (possibly new) head.

Q5. Why do LRU caches pair a hash map with a doubly linked list?

The map gives O(1) jump-to-node by key; the DLL gives O(1) unhook/move-to-front for the node you jumped to (it knows both neighbors). Together: O(1) get and put with eviction order maintained.
