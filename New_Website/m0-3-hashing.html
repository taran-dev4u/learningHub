Module 0.3 — Hash Maps & Hash Sets (Internals)

The hash map is the single most-used tool in interview problems: it trades a little memory for the magical ability to answer "have I seen this before?" in constant time. Here you'll learn how the magic works — and when it breaks.

1. Why this exists

Analogy. A coat-check at a theater. You hand over your coat, the attendant computes a hook number from your ticket, and hangs it there. When you return, no one searches the racks — the ticket number leads straight to the hook. A hash map is a coat-check for data: the "ticket math" is the hash function, the hooks are array slots.

The problem it solves. Arrays give O(1) access only if you know the position. But most questions are by value: "is this username taken?", "how many times did 'cat' appear?" In an array those cost O(n) per lookup. A hash map makes lookup-by-key O(1) on average — it converts the key itself into a position.

Plain-English definition. A hash map (dictionary) stores key → value pairs. A hash function turns any key into an array index; the pair lives in (or near) that slot. A hash set is the same machine storing only keys, answering membership questions.

2. The hash function

A hash function maps a key (string, number, tuple…) to a fixed-size integer, and the table reduces it to a slot with modulo:

key "cat" ──hash()──▶ 8838103  ──% 8 (table size)──▶ slot 7

Requirements of a good hash function:
  1. DETERMINISTIC  — same key, same hash, always
  2. FAST           — O(length of key)
  3. UNIFORM        — spreads keys evenly over slots (no crowding)
def simple_string_hash(s, table_size):
    h = 0
    for ch in s:
        # 31 is a small prime; multiplying mixes previous chars into
        # higher "digits" so "ab" and "ba" hash differently
        h = (h * 31 + ord(ch)) % table_size
    return h

Dry run, table_size = 8: "cat" → h = 0; h = 0·31+99 = 99 → 99%8 = 3; h = 3·31+97 = 190 → 190%8 = 6; h = 6·31+116 = 302 → 302%8 = 6. "cat" lands in slot 6. Same input always lands in slot 6 — that's determinism.

3. Collisions — when two keys want the same slot

Why collisions are unavoidable: there are infinitely many possible keys and finitely many slots, so some keys must share (the pigeonhole principle). The question is only how to handle sharing gracefully. Two classic strategies:

3.1 Chaining — each slot holds a list

table size 4, after inserting ("cat",1) ("dog",2) ("owl",3)
where hash(cat)=2, hash(dog)=0, hash(owl)=2   ← cat & owl COLLIDE

  slot 0:  [("dog", 2)]
  slot 1:  []
  slot 2:  [("cat", 1), ("owl", 3)]   ← both live here, in a chain
  slot 3:  []

lookup "owl": hash → slot 2 → walk the short chain: cat? no → owl? yes ✓

3.2 Open addressing — go find the next free slot

insert "owl" (wants slot 2, occupied):

  slot:   0      1      2      3
        [dog]  [   ]  [cat]  [   ]
                        ▲ taken → probe next → slot 3 free → place there

lookup "owl": slot 2? cat, not owl → keep probing → slot 3 ✓
(deletes need a TOMBSTONE marker, or probing chains would break)

4. Load factor & rehashing

Analogy. The coat-check works because hooks outnumber crowds. When 90% of hooks are taken, the attendant starts hanging coats two-deep and service slows. Solution: move to a bigger rack before it gets bad.

Load factor = entries ÷ slots. As it rises, collisions multiply and chains lengthen. When it crosses a threshold (Python: ~2/3), the table rehashes: allocate a table ~2× larger and re-insert every key (hashes change because % table_size changed!).

load factor 2/8           load factor 6/8 (crowded!)        after rehash: 6/16
[a][ ][ ][b][ ][ ][ ][ ]  [a][c][e][b][d][f][ ][ ]   →   spread thin again ✓
fast: most slots free      probes get long                  O(n) one-time cost

Why lookups stay O(1) on average: the same amortized argument as dynamic arrays (Module 0.2) — rehashing is O(n) but happens only after Θ(n) cheap inserts, so each insert pays O(1) on average, and the load factor cap keeps expected probe/chain length constant.

5. Build a hash map from scratch (chaining)

class HashMap:
    def __init__(self):
        self.size = 0
        self.capacity = 8
        self.buckets = [[] for _ in range(8)]   # one chain (list) per slot

    def _bucket(self, key):
        return self.buckets[hash(key) % self.capacity]  # key → its chain

    def put(self, key, value):                  # insert OR update
        bucket = self._bucket(key)
        for i, (k, v) in enumerate(bucket):
            if k == key:                        # key exists → UPDATE in place
                bucket[i] = (key, value)
                return
        bucket.append((key, value))             # new key → INSERT at chain end
        self.size += 1
        if self.size / self.capacity > 0.66:    # load factor check
            self._rehash()

    def get(self, key, default=None):           # access / search
        for k, v in self._bucket(key):          # walk the (short) chain
            if k == key:
                return v
        return default

    def contains(self, key):
        return any(k == key for k, _ in self._bucket(key))

    def delete(self, key):
        bucket = self._bucket(key)
        for i, (k, v) in enumerate(bucket):
            if k == key:
                bucket.pop(i)                   # O(chain length) ≈ O(1)
                self.size -= 1
                return True
        return False

    def keys(self):                             # traverse: every chain
        for bucket in self.buckets:
            for k, _ in bucket:
                yield k                         # O(capacity + size)

    def _rehash(self):
        old = self.buckets
        self.capacity *= 2                      # bigger table → lower load factor
        self.buckets = [[] for _ in range(self.capacity)]
        for bucket in old:
            for k, v in bucket:                 # re-insert: slots move because
                self._bucket(k).append((k, v))  # hash(k) % capacity changed

Dry run. put("cat", 1): hash("cat") % 8 = say 6 → chain at slot 6 is empty → append ("cat",1). put("owl", 3) also → slot 6 → chain now has cat; owl ≠ cat → append → chain [("cat",1),("owl",3)]. get("owl"): slot 6 → check cat (no) → owl (yes) → return 3. Two key-comparisons, regardless of whether the map holds 10 or 10 million other entries — that's the whole point.

When O(1) degradesIf many keys hash to the same slot — a terrible hash function, or an adversary crafting collisions — every operation becomes a walk through one giant chain: O(n). Interviews expect you to say "O(1) average, O(n) worst case" unprompted.

6. Python's dict, set, and friends

d = {}                       # hash map
d["cat"] = 1                 # put / update          O(1) avg
d["cat"]                     # get (KeyError if absent)
d.get("dog", 0)              # get with default — no exception
"cat" in d                   # membership            O(1) avg
del d["cat"]                 # delete (KeyError if absent)
for k, v in d.items(): ...   # traverse              O(n)

s = set()                    # hash set: keys only
s.add(3); s.discard(3)       # discard never raises; remove() does
3 in s                       # O(1) avg

from collections import defaultdict, Counter
freq = defaultdict(int)      # missing key → 0 automatically
freq["a"] += 1               # no "if key not in" dance
Counter("banana")            # Counter({'a':3, 'n':2, 'b':1}) — instant frequency map
Counter(s1) == Counter(s2)   # anagram check in one line
Keys must be hashable (immutable)Lists and dicts can't be keys — if a key mutated after insertion, its hash would change and the table could never find it again. Use tuples instead: d[(row, col)] = v, d[tuple(sorted(word))]. This is exactly why Python strings are immutable (Module 0.2).

7. The three moves hash maps win with

Move 1: Have I seen this? (set)

def has_duplicate(nums):
    seen = set()
    for x in nums:
        if x in seen:        # O(1) — vs O(n) scan; whole loop O(n) vs O(n²)
            return True
        seen.add(x)
    return False

Move 2: Count occurrences (frequency map)

freq = {}
for x in nums:
    freq[x] = freq.get(x, 0) + 1   # one O(n) pass answers "how many of each?"

Move 3: Remember where / what was paired (key → info)

def two_sum(nums, target):           # the most famous interview problem
    seen = {}                        # value → index of where we saw it
    for i, x in enumerate(nums):
        if target - x in seen:       # is my partner already behind me?
            return [seen[target - x], i]
        seen[x] = i                  # remember me for future partners
    # one pass, O(n) — the brute force pair-check is O(n²)

Dry run on nums=[2,7,11,15], target=9: i=0, x=2: need 7, not seen → store {2:0}. i=1, x=7: need 2 — in seen! → return [0,1]. The map replaced an entire inner loop.

9. Edge cases & classic mistakes

  • Missing keys. d[k] raises KeyError. Use d.get(k, default) or defaultdict.
  • Mutating while iterating. Adding/removing dict keys inside for k in d raises RuntimeError. Iterate over list(d).
  • Unhashable keys. d[[1,2]] → TypeError. Convert to tuple.
  • Assuming sorted order. dict preserves insertion order (Python ≥3.7), never sorted order.
  • Empty input. max(freq.values()) on an empty map crashes.
  • Float keys. Rounding makes 0.1 + 0.2 != 0.3 — equality-by-hash on floats is fragile. Prefer ints/strings/tuples.
  • defaultdict side effect. Merely reading dd[k] creates the key. Use k in dd for pure checks.

10. When to use / recognition signals

Reach for a hash map/set when the problem says…"have we seen", "duplicate", "count / frequency / most common", "anagram", "pair that sums to", "group by", "first unique", "O(1) lookup", or whenever you're tempted to write a nested loop that just re-finds something you already passed.
Avoid when…you need sorted order or range queries (tree / sorted array + binary search), the keys are tiny dense integers (a plain array indexed by value is faster and simpler), or worst-case guarantees are required (balanced BST).

11. Check yourself

Q1. Why can't a list be a dict key?

Lists are mutable. If the list changed after insertion, its hash would change, and the table would look in the wrong slot forever. Only immutable (hashable) objects — strings, numbers, tuples of immutables — can be keys.

Q2. What is a load factor, and why rehash at ~2/3 rather than waiting until full?

Load factor = entries/slots. As it grows, collisions and probe lengths grow; past a point, average operations stop being O(1). Resizing early keeps expected chain/probe length constant. The O(n) rehash amortizes to O(1) per insert.

Q3. Two Sum: why does one pass with a map beat two nested loops?

The inner loop's only job was to search for the complement — O(n) each time. The map answers the same search in O(1) by remembering everything already seen, so n × O(1) replaces n × O(n).

Q4. When would a hash map be the wrong choice for fast lookups?

When you need sorted traversal, predecessor/successor, or range queries — hash scatters keys deliberately, destroying order. Use a balanced BST/TreeMap (O(log n)) or a sorted array with binary search.

Q5. Chaining vs open addressing — name one advantage of each.

Chaining: deletion is trivial and the table tolerates load factor > 1. Open addressing: better memory locality (no pointers, everything in one array), so it's faster in practice at low load factors.
