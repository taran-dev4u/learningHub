# Distributed Transactions & Sagas

In a monolithic application with a single relational database, ensuring data integrity is a solved problem. You wrap your database operations in an **ACID transaction**. You deduct $100 from Alice's account, add $100 to Bob's account, and hit `COMMIT`. If the database crashes midway, the transaction rolls back. It's safe, atomic, and magical.

But welcome to the world of Microservices.

Now, Alice's account is managed by the `User-Service` (with its own PostgreSQL DB), Bob's account is in the `Payment-Service` (using MySQL), and the receipt is generated by the `Notification-Service` (using MongoDB). A single business action now spans three isolated databases over a flaky network. How do we ensure that money isn't deducted from Alice without ever reaching Bob?

Handling transactions across multiple distributed systems is one of the hardest challenges in system design. Let's explore the solutions, their massive trade-offs, and how modern tech giants handle them.

---

## The Legacy Approach: Two-Phase Commit (2PC)

If you must have strict ACID guarantees across multiple databases, the traditional protocol is the **Two-Phase Commit (2PC)**.

As the name implies, it breaks the commit process into two distinct phases, managed by a central **Transaction Coordinator**.

1. **Phase 1: Prepare (Voting Phase)**
   - The Coordinator tells all participating databases: "Prepare to commit this transaction. Lock your rows and write your intentions to disk. Reply YES if you are ready, NO if you hit an error."
   - The databases acquire heavy write locks on the rows (e.g., Alice's balance).

2. **Phase 2: Commit (Completion Phase)**
   - If *all* participants replied YES, the Coordinator broadcasts: "COMMIT!" The databases finalize the write and release the locks.
   - If *any* participant replied NO (or timed out), the Coordinator broadcasts: "ABORT!" Everyone rolls back.

### The Fatal Flaw of 2PC: Blocking
2PC guarantees strict consistency, but its availability is abysmal.
Imagine the Coordinator sends the "Prepare" command, all databases lock their rows, reply YES, and then... the Coordinator crashes before sending the "Commit" command.
The participating databases are now stuck. They cannot release their locks, because they don't know if the transaction was ultimately approved or aborted. Alice's account is locked indefinitely until the Coordinator recovers.

> [!WARNING]
> **Common Beginner Mistake**
> Do not suggest Two-Phase Commit (2PC) in a microservices system design interview unless you explicitly highlight that it is a massive bottleneck. Modern scalable systems almost *never* use distributed locks like 2PC because the latency and blocking characteristics destroy system throughput.

## The Modern Approach: The SAGA Pattern

If 2PC is out, how do we handle distributed transactions? The answer is we abandon strict ACID atomicity in favor of **Eventual Consistency** and **Compensating Actions**. This is known as the **SAGA Pattern**.

A Saga is a sequence of local transactions. Each service updates its own database independently and publishes an event/message to trigger the next step in the saga. There is no global lock.

### How a Saga works (Choreography Example):
1. **Order Service** receives checkout request, creates an Order in `PENDING` state, and emits `OrderCreatedEvent`.
2. **Payment Service** listens to the event, charges the credit card, and emits `PaymentSuccessEvent`.
3. **Inventory Service** listens, reserves the items, and emits `InventoryReservedEvent`.
4. **Order Service** listens, updates the Order state to `CONFIRMED`.

### What if something fails? (Compensating Actions)
Because there are no global locks, if a step fails, you cannot simply `ROLLBACK` the database. The previous steps have already committed their data! Instead, you must issue a **Compensating Transaction** to reverse the business action.

Imagine the Payment succeeded, but the Inventory Service realizes the item is out of stock:
1. **Inventory Service** emits `InventoryFailedEvent`.
2. **Payment Service** listens, and issues a *Refund* to the credit card (this is the compensating action).
3. **Order Service** listens, and updates the Order state to `CANCELLED`.

> [!TIP]
> **Orchestration vs. Choreography**
> In **Choreography**, services listen to each other's events directly (like a dance). It's decentralized but can become a tangled mess to debug.
> In **Orchestration**, a central "Saga Execution Coordinator" (like AWS Step Functions or Netflix Conductor) explicitly commands each service what to do and handles the rollback logic centrally. Orchestration is heavily preferred for complex workflows.

## The Transactional Outbox Pattern

In a Saga, a service often needs to do two things simultaneously:
1. Write a business entity to its database (e.g., `INSERT INTO orders`).
2. Publish an event to Kafka/RabbitMQ (e.g., `publish('OrderCreated')`).

You cannot wrap a DB insert and a Kafka publish in a single ACID transaction. If the DB commits, but the network drops before Kafka receives the message, the rest of the saga never triggers! Your system is now in an inconsistent state.

**The Solution: Transactional Outbox**
1. Create a table in your DB called `outbox`.
2. When creating an order, open a standard local database transaction.
3. `INSERT INTO orders` AND `INSERT INTO outbox (event_data)` in the *same* local transaction.
4. Commit the local transaction. (This is atomic!).
5. A separate background process (like Debezium, or a polling cron job) constantly reads the `outbox` table and safely pushes those messages to Kafka. Once successfully pushed, it marks the outbox row as processed.

This guarantees that if the business data is written, the event *will* eventually be published. This is known as **At-Least-Once Delivery**.

## Handling Concurrency: Vector Clocks

When distributed systems ditch strict locks, they have to deal with concurrent updates. If Node A and Node B both try to update a shopping cart at the exact same millisecond, which write wins?

Simple timestamps are dangerous because server clocks drift (NTP isn't perfectly synchronized). To solve this, distributed databases like DynamoDB and Riak use **Vector Clocks**.

A Vector Clock tracks the history of updates using logical counters instead of time. It looks like a list of node IDs and their counters: `[NodeA: 2, NodeB: 1]`.

1. When a client reads data, it receives the Vector Clock.
2. When it writes data back, it passes the clock back to the server.
3. The server compares the clocks. If the new clock clearly descended from the old clock (e.g., `[NodeA: 3, NodeB: 1]`), the write is accepted safely.
4. If two clients updated the same data concurrently on different nodes, their clocks will conflict (e.g., `[NodeA: 3, NodeB: 1]` vs `[NodeA: 2, NodeB: 2]`).
5. The database detects this **concurrent collision** and usually returns both versions to the client, forcing the client application to resolve the conflict (e.g., merge the two shopping carts).

## Trade-off Summary

| Pattern | Consistency | Performance | Complexity | Best Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **Two-Phase Commit (2PC)** | Strong (ACID) | Terrible (Blocking Locks) | Medium | Legacy internal financial systems on fast LANs |
| **SAGA Pattern** | Eventual | Excellent | Very High | Microservices architectures, modern cloud apps |
| **Transactional Outbox** | Strong local, Eventual global | Great | High | Publishing events reliably from microservices |

> [!NOTE]
> **Teacher FAQ: Do big banks use SAGAs or 2PC?**
> People assume banks strictly use distributed locking because "it's money." In reality, high-scale financial systems rely heavily on Sagas, async messaging, and reconciliation engines. If you transfer money between two different banks, it's not a synchronous 2PC blocking transaction. Your bank deducts it locally, sends an async message via a clearinghouse, and the receiving bank adds it hours or days later. If something fails, compensating actions (reversals/refunds) are triggered.
