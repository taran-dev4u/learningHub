Behavioral Story Methods

5 items
How to turn experience into concise stories.
  1. ☆
    STAR method
    Situation (context & stakes), Task (your explicit role), Action (60% of time: decisions, trade-offs, technical steps), Result (quantified business impact). Default for FAANG behavioral.
    YTGoogle
  2. ☆
    CARL method
    Context (the setup), Action (what you owned), Result (measured outcome), Learning (reflection on what you would do differently and how it matured your engineering judgment).
    YTGoogle
  3. ☆
    SOAR method
    Situation, Obstacle (the unexpected blocker or failure), Action (mitigation & recovery steps), Result. Best for adversity, conflict, and post-mortem questions.
    YTGoogle
  4. ☆
    PAR method
    Problem, Action, Result. High-density 60-second format ideal for initial recruiter screens and lightning-round behavioral checks.
    YTGoogle
  5. ☆
    Result plus reflection
    Always conclude with dual results: 1. Quantitative metric (e.g. -45% p99 latency, +$1.2M GMV); 2. Systemic learning instituted to prevent recurrence.
    YTGoogle

Direct Answer Methods

5 items
How to answer open-ended and opinion questions without rambling.
  1. ☆
    PREP method
    Point (direct conclusion), Reason (the underlying architectural principle), Example (concrete production scenario), Point (reiterating the takeaway).
    YTGoogle
  2. ☆
    PEEL method
    Point (claim), Evidence (data/metrics), Explanation (why the evidence supports the point), Link (connecting back to the broader problem).
    YTGoogle
  3. ☆
    Headline first
    State your bottom-line conclusion in the first 10 seconds before providing background; prevents losing the interviewer's attention.
    YTGoogle
  4. ☆
    Signposting
    Outline the 2-3 parts of your answer up front ('I approached this through 3 phases: root cause profiling, canary mitigation, and systemic linting').
    YTGoogle
  5. ☆
    Time-boxing
    Calibrate story duration strictly: 30s elevator summary, 90s standard response, 3min project deep-dive; stop and check in with the interviewer.
    YTGoogle

Trade-Off and Judgment Questions

5 items
Show senior reasoning in simple language.
  1. ☆
    Why did you choose this technology

  2. ☆
    What did you optimize for
    State explicit priority ranking: Reliability > Security > Latency > Cost > Feature Velocity; explain why this ordering fit the business phase.

    What broke at scale

  4. ☆
    How do you handle incidents

    How do you decide build vs buy
    Framework: Buy commodity capabilities (auth, billing, email, observability) to preserve focus; Build core differentiators (proprietary algorithms, business logic, core storage).

Coding Interview Communication

    Close with complexity and tests

    [GenAI Systems] How do you calculate and eliminate KV cache memory fragmentation in LLM inference serving (PagedAttention & vLLM)?

    TL;DR: KV cache size scales linearly with sequence length, batch size, layers, and hidden dimensions, consuming up to 60-80% of GPU VRAM during serving. Virtual memory paging algorithms like PagedAttention eliminate internal and external fragmentation by allocating KV blocks non-contiguously in memory.

    Core Mechanism: In Multi-Head Attention (MHA), each generated token stores key and value vectors. The memory required per token is given by: 2 * 2 bytes (FP16) * n_layers * n_heads * d_head. For Llama-3-70B (80 layers, 64 heads, d_head=128), a single token takes ~1.31 MB across all layers. Traditional frameworks pre-allocated contiguous memory for the maximum possible sequence length (e.g. 8k tokens = 10.5 GB per request), causing 60-80% memory waste due to internal/external fragmentation and reservation overestimation. PagedAttention divides the KV cache into fixed-size virtual blocks (typically 16 or 32 tokens). A central Block Table maps virtual token positions to non-contiguous physical GPU DRAM pages, dynamically fetching blocks on-demand during decoding and enabling copy-on-write sharing across parallel beams and prefix prompts.

    Trade-offs & Failure Modes: Smaller block sizes (e.g., 8 tokens) minimize memory fragmentation but increase block table lookup overhead in CUDA kernels and reduce tensor core coalesced memory access throughput. Larger block sizes (e.g., 64 tokens) maximize GPU memory bandwidth utilization but re-introduce internal fragmentation for short user queries.

    Production Impact: Adopting PagedAttention in vLLM increases serving throughput by 2.5x to 4x over naive Hugging Face Transformers, reduces GPU memory waste from 73% to <4%, and enables serving batch sizes of 128+ concurrent streams on an 8x A100 (80GB) node.

    [GenAI Systems] How does Continuous / Dynamic Batching disaggregate Prefill from Decode phases to optimize TTFT and ITL?

    TL;DR: Static batching locks all requests to the slowest generating request; continuous iteration-level scheduling inserts new requests into running batches at every decoding step, disaggregating prefill (compute-bound) from decode (memory-bandwidth bound) phases.

    Core Mechanism: LLM inference has two distinct phases: 1. Prefill (Prompt Phase): Processes all prompt tokens in parallel, fully saturating GPU tensor cores (compute-bound, arithmetic intensity > 100 FLOP/byte). 2. Decode Phase: Generates one token at a time autoregressively per sequence, constrained by memory bus bandwidth (memory-bound, arithmetic intensity ~ 1 FLOP/byte). Under static batching, if 4 requests have lengths [10, 50, 100, 500], the GPU idles 3 slots while waiting for the 500-token generation. Continuous batching (iteration-level scheduling) evaluates batch membership at every token step: when request A finishes, slot A is instantly replaced with the prefill phase of request E. Advanced architectures (e.g., vLLM chunked prefill, Mooncake, DistServe) physically disaggregate prefill and decode across separate GPU clusters, routing prefill to high-compute H100s and decode to bandwidth-optimized nodes connected via RDMA.

    Trade-offs & Failure Modes: Co-locating prefill and decode on the same GPU causes prefill spikes to preempt decoding iterations, spiking Inter-Token Latency (ITL) and causing noticeable generation stuttering for active streaming users. Physical cluster disaggregation eliminates ITL jitter but introduces KV cache network transfer overhead over NVLink/InfiniBand.

    Production Impact: Continuous batching achieves 3x to 5x higher token throughput compared to static batching. Prefill-decode disaggregation maintains p99 ITL < 25ms while reducing Time to First Token (TTFT) by 40% under 95% GPU load.

    [GenAI Systems] How does Speculative Decoding achieve 2-3x latency reduction without degrading model output distribution?

    TL;DR: Speculative decoding uses a lightweight, fast draft model to speculate K candidate tokens autoregressively, then verifies all K tokens in a single forward pass of the larger target model, preserving the target model's exact probability distribution.

    Core Mechanism: Autoregressive decoding is bound by memory bandwidth: transferring 70B parameters from DRAM to SRAM takes ~35ms on an A100 just to produce a single token. Speculative decoding pairs a small draft model (e.g., Llama-3-8B) with a large target model (e.g., Llama-3-70B). The draft model speculates K tokens (e.g., K=5) in fast succession (~5ms total). The target model then runs a single batched prefill pass across all K candidate tokens in parallel. If the draft token probability q(x) and target probability p(x) satisfy a rejection sampling criterion (accept if U < min(1, p(x)/q(x))), the token is accepted. When token i is rejected, a replacement token is sampled from max(0, p(x) - q(x)) and subsequent speculative tokens are discarded. Because of the exact rejection sampling mathematics, the output distribution is mathematically identical to running the 70B target model alone.

    Trade-offs & Failure Modes: If the draft model alignment or domain accuracy is low (acceptance rate alpha < 50%), verification overhead outweighs speculation gains, resulting in slower generation than vanilla inference. In high-concurrency multi-tenant serving, GPU compute is saturated by batching, diminishing speculative decoding gains which primarily accelerate low-batch latency.

    Production Impact: Under batch size = 1 on code and structured summarization workloads with an acceptance rate alpha ~ 75-80%, speculative decoding reduces end-to-end p50 generation latency by 2.2x to 2.8x with 0.0% divergence in output perplexity.

    [GenAI Systems] What are the architectural differences between AWQ, GPTQ, and SmoothQuant for low-bit LLM quantization?

    TL;DR: GPTQ uses second-order Hessian error minimization for weight-only INT4; AWQ protects salient 1% activation outlier weights; SmoothQuant scales activation outliers into weights to enable true INT8/INT8 weight-activation matrix multiplication.

    Core Mechanism: Post-Training Quantization (PTQ) maps FP16 (16-bit) weights and activations to INT8 or INT4. 1. GPTQ (Generative Pre-trained Transformer Quantization): Optimizes weight-only quantization layer-by-layer using an inverted Hessian matrix H^{-1} = (2 X X^T + lambda I)^{-1} to greedily compensate remaining unquantized weights for the quantization error of rounded weights. 2. AWQ (Activation-aware Weight Quantization): Observes that not all weights are equally important; protecting the top 1% of weights corresponding to high-magnitude activation channels prevents perplexity degradation. AWQ calculates per-channel scaling factors s to minimize output error without altering activations. 3. SmoothQuant: Quantizing activations to INT8 is difficult because activation channels exhibit systematic, high-magnitude outliers (>100x normal values). SmoothQuant applies a per-channel mathematically equivalent transformation Y = (X diag(s)^{-1}) * (diag(s) W), smoothing activation spikes into the weight matrix and unlocking hardware-accelerated W8A8 INT8 Tensor Core GEMM.

    Trade-offs & Failure Modes: Weight-only quantization (AWQ/GPTQ INT4) reduces GPU memory footprint by 70% and accelerates memory-bound decode phases, but compute-bound prefill phases still require on-the-fly dequantization to FP16 in registers.     [GenAI Systems] How do FlashAttention-2 and Grouped-Query Attention (GQA) overcome GPU memory bandwidth bottlenecks?

    TL;DR: FlashAttention uses SRAM tiling and online softmax to avoid materialized N x N attention matrices in slow High Bandwidth Memory (HBM); Grouped-Query Attention shares key/value heads across query head groups to slash KV cache memory traffic.

    Core Mechanism: Standard multi-head attention computes Attention(Q, K, V) = softmax(Q K^T / sqrt(d)) V. Storing the intermediate attention matrix S = Q K^T of shape (Batch, Heads, N, N) requires writing and reading O(N^2) elements to slow GPU HBM, making it memory-bound. FlashAttention tiles Q, K, and V into SRAM blocks (20 TB/s bandwidth vs 2 TB/s HBM), executing matrix multiplication, scaling, and online softmax normalization in fast on-chip SRAM via a 2-pass online rescale trick: m_new = max(m_prev, x), l_new = exp(m_prev - m_new) * l_prev + sum(exp(x - m_new)). FlashAttention-2 optimizes work partitioning across thread blocks to reach 73% of theoretical peak GPU FLOPs. Grouped-Query Attention (GQA) modifies the transformer architecture: instead of each Query head having its own Key/Value head (MHA), GQA groups H query heads to share a single Key/Value head (e.g. 8 KV heads for 64 Q heads in Llama-3-70B), reducing KV cache memory load by 8x.

    Trade-offs & Failure Modes: GQA requires architectural model retraining or up-training from checkpoint; it cannot be applied retroactively to an existing pure MHA checkpoint without fine-tuning. FlashAttention requires compute capability >= SM80 (Ampere/Hopper) and fixed head dimensions (<= 256).

    Production Impact: FlashAttention-2 provides 2x to 4x end-to-end training and inference speedups over vanilla attention at 8k context, scaling sub-quadratically in memory IO. GQA reduces KV cache memory consumption by 87.5% (8x reduction), cutting latency per token by 45% under high concurrent concurrency.

    [GenAI Systems] How does QLoRA achieve 16-bit fine-tuning performance on a single consumer GPU using 4-bit NormalFloat?

    TL;DR: QLoRA freezes the base model quantized to 4-bit NormalFloat (NF4), inserts trainable FP16 low-rank adapter matrices (LoRA), and utilizes Double Quantization and Paged Optimizers to eliminate memory spikes during backward passes.

    Core Mechanism: Full parameter fine-tuning of a 70B model requires ~140 GB for weights, ~280 GB for optimizer states (AdamW), and ~140 GB for gradients, requiring a cluster of multi-GPU nodes (>600 GB VRAM). QLoRA solves this with three innovations: 1. 4-bit NormalFloat (NF4): An information-theoretically optimal quantile quantization data type for normally distributed neural network weights, ensuring equal information capacity per bin. 2. Double Quantization (DQ): Quantizes the quantization constants themselves, reducing memory footprint by 0.37 bits per parameter (~3 GB savings for 70B). 3. Paged Optimizers: Uses CUDA Unified Memory to automatically page AdamW 32-bit optimizer states from GPU VRAM to CPU RAM during non-critical backprop stages. Only the adapter weights W = W_0 + (alpha / r) * (B * A) (where B in R^{d x r}, A in R^{r x k}, rank r << d) accumulate gradients in FP16/BF16.

    Trade-offs & Failure Modes: On-the-fly dequantization of NF4 weights to FP16 during forward and backward passes adds ~20-30% compute overhead compared to unquantized LoRA. High rank r (>64) or adapting all linear layers increases adapter memory without proportional accuracy gains.

    Production Impact: Fine-tunes a 70B model on a single 48GB GPU (or dual 24GB GPUs) instead of an 8x 80GB cluster (cutting hardware cost by 85%), retaining 99.3% of full 16-bit fine-tuning accuracy across Vicuna and Alpaca benchmarks.

    [GenAI Systems] How does Direct Preference Optimization (DPO) mathematically bypass the instability of RLHF PPO training?

    TL;DR: DPO derives a closed-form substitution that expresses the reward function directly in terms of the optimal policy ratio, replacing the complex 4-model PPO reinforcement learning pipeline with a stable binary cross-entropy loss.

    Core Mechanism: Classical RLHF uses Proximal Policy Optimization (PPO), which requires instantiating 4 separate models in memory simultaneously: the Actor (policy being trained), Critic (value network), Reward Model (trained on human rankings), and Reference Model (frozen base policy for KL divergence penalty). PPO is notoriously unstable due to high variance gradient estimates and hyperparameter sensitivity. DPO demonstrates that the Bradley-Terry preference model P(y_w > y_l | x) = sigma(r(x, y_w) - r(x, y_l)) can be inverted. By substituting the analytical solution r(x, y) = beta * log(pi(y|x) / pi_ref(y|x)) into the Bradley-Terry likelihood, DPO formulates a direct loss: L_DPO(theta) = - E_{(x, y_w, y_l)} [ log sigma( beta * log(pi_theta(y_w|x) / pi_ref(y_w|x)) - beta * log(pi_theta(y_l|x) / pi_ref(y_l|x)) ) ]. This completely eliminates the Critic and Reward models.

    Trade-offs & Failure Modes: DPO is offline: it optimizes only on static, pre-collected preference pairs. If the dataset contains noisy or low-quality negative examples, DPO can overfit and collapse probabilities on valid alternative completions. Online PPO/RLAIF can explore new token paths beyond the initial dataset.

    Production Impact: DPO slashes VRAM requirements by 50% during alignment, speeds up training by 3x compared to PPO, and achieves equal or superior Win Rates on MT-Bench and AlpacaEval with zero policy divergence collapses.

    [AI System Design] How do you design a real-time Copilot code autocomplete system with a strict sub-100ms p99 latency budget?

    TL;DR: Meet sub-100ms budgets by enforcing Fill-in-the-Middle (FIM) prompt representations, client-side debounce triggers, speculative prefix caching, and specialized quantized 3B-7B models served on high-bandwidth memory GPUs.

    Core Mechanism: Developers type at 60-120 WPM; autocomplete must display suggestions in <100ms, otherwise it disrupts developer flow. Latency Budget: Network RTT (30ms) + Client preprocessing (10ms) + Inference TTFT (40ms) + Client render (10ms) = 90ms. Architecture: 1.
